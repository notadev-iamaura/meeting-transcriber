## 1. 목표와 범위

이번 개선의 목표는 **기존 회의 기록을 믿고 수정·검색·복구할 수 있고, 처리 상태를
이해하며, 설치 후 첫 회의를 끝까지 완료할 수 있는 제품**을 만드는 것이다.

완료 판단은 다음 사용자 행동을 기준으로 한다.

1. 잘못된 금액·담당자를 수정하면 검색과 답변에도 수정본이 반영된다.
2. 회의·날짜·화자를 지정한 질문은 그 범위 안의 근거만 사용한다.
3. 검색 장애를 감지하고 원본을 보존한 채 복구할 수 있다.
4. 긴 작업의 대기·실패 이유와 가능한 다음 행동을 이해할 수 있다.
5. 저장된 회의 자산을 다른 로컬 위치에서 복원할 수 있다.
6. 신규 사용자가 필요한 준비만 마치고 정상 녹음·전사·근거 확인을 완료한다.

수익화, 결제, 광고, 팀 동기화, Windows 지원, 새 모델 추가는 후속 사업 계획에서
다룬다. 이번 작업은 현재 기능의 신뢰성과 사용성 개선에 집중한다.
제품 코드 수정·환경 설치·서버 실행·배포는 이 계획서 작성에 포함하지 않았다.

| 단계 | 목표 | 주요 작업 | 다음 단계로 넘어가는 조건 |

첫 구현 차수의 범위는 **A+B**다. C+D는 후속 차수로 유지한다.
IMP-01/03/05는 IMP-00 이후 서로 독립적으로 검증할 수 있지만, 같은 파일을 만지는
구현은 별도 변경 단위로 통합한다. IMP-02/04/06은 저장·검색 상태 계약을 먼저
합의하고 순서대로 진행한다. 여러 에이전트 실행 여부와 무관한 의존관계다.

달력 일정은 아직 확정하지 않는다. A 단계가 끝나면 실제 설치 시간, 통합 재현 결과,
IMP-02 데이터 변경 범위에 따라 첫 차수의 예상 기간을 산정한다. 날짜가 도래했다는
이유로 미통과 검증을 생략하지 않는다.

## 4. 첫 차수의 구현 단위

### IMP-00 — 검증 환경과 재현 기반

- 지원 Python 3.11/3.12, 프로젝트 의존성, Chroma 버전, ffmpeg와 브라우저 가용성을
  확인하고 실제 사용한 버전을 기록한다. 기존 실행 환경이 있으면 먼저 재사용 가능성을 확인한다.
- 테스트 데이터는 임시 MT_BASE_DIR에 격리한다. 실제 사용자 회의·Keychain·오디오
  장치를 테스트 fixture로 사용하지 않는다. 테스트 런타임은 기존 api-test/unit-test 경로를 활용한다.
- 기존 좁은 테스트를 먼저 실행한다. 현재 실패하는 테스트는 원인과 재현 조건을 남겨
  이번 변경으로 생긴 실패와 구분한다.
- 이전 감사의 AST/stub 스크립트는 문제 설명용으로 유지하고 실제 FastAPI 및
  SQLite/Chroma 통합 회귀로 옮긴다. 테스트용 임베딩은 고정값으로 주입해 모델 다운로드를 피한다.
- **완료:** 명령·버전·통과/실패/미실행 이유가 기록되고, 첫 차수의 결함을 실제
  해당 계층에서 재현할 수 있다. 패키지 설치가 막히면 보안 우회 없이 환경 장애로 기록한다.

### IMP-01 — WebSocket 연결 경계

- 대상: `api/websocket.py`, `api/server.py`, 기존 loopback helper, 네이티브 연결 계약.
- 정상 브라우저와 pywebview가 보내는 Origin/Host를 실제로 확인한 뒤 허용 규칙을
  정한다. 다른 포트의 localhost를 무조건 신뢰하지 않도록 scheme/host/port를 구분한다.
- accept 이전에 부적절한 출처를 거부한다. Origin 누락/null을 정상 네이티브라는
  이유만으로 포괄 허용하지 않고 필요한 경우 검증 가능한 세션 경로를 설계한다.
- 재연결·최대 연결 수·앱 종료 동작을 보존한다. 이벤트의 절대경로 등 불필요한
  메타데이터를 줄일 때 소비 UI와의 호환도 확인한다.
- **완료:** 허용 출처의 최초 연결/재연결 성공, 거부 출처의 이벤트 수신 0건,
  Origin 없음/null/Host 변조 테스트, 정상 네이티브 연결 확인.
- HTTP 변경 요청 전체의 공통 경계는 후속 보안 범위로 기록한다. WS 수정 한 건을
  전체 HTTP 인증·CSRF 해결로 보고하지 않는다.

### IMP-02 — 원문 변경과 검색 최신성

- 대상: 전사 PUT/replace, `core/reindex_recovery.py`, 회의 메타데이터,
  검색 reader/writer, viewer·상태 API.
- 원문 버전과 두 검색 인덱스의 반영 버전을 연결한다. 내부 상태는 최소한
  최신/갱신 필요/갱신 중/실패/판정 불가를 구별하고 UI에는 일상 언어로 표시한다.
- 내구성 있는 변경 의도를 먼저 남기고 원문을 게시한 뒤 순차 재색인을 등록한다.
  파일·SQLite·Chroma는 하나의 원자 transaction이 아니므로 단계별 종료와 재시작을 고려한다.
- 기존 `reindex_required.json`은 재전사·삭제 복구에서 사용하는 계약이 있으므로,
  무조건 덮어쓰거나 편집 큐용으로 재해석하지 않는다. 재사용/확장/별도 기록 중
  최소 변경안을 설계 문서로 결정한다.
- 같은 회의의 빠른 연속 편집은 최신 원문으로 수렴시킨다. 이전 재색인이 나중에
  끝나도 최신 상태를 덮지 못해야 한다. 기존 회의별 lease와 단일 모델 로드를 유지한다.
- 검색 갱신 중에는 오래된 내용을 최신 원문인 것처럼 답하지 않는다. 영향 회의는
  최신 인덱스 확인 전 검색/답변에서 제외하고 사용자에게 갱신 상태를 알리는 안을 우선한다.
- 기존 요약·Wiki 파생 결과도 최신으로 오인되지 않도록 원문 변경 이후 검토 필요를
  표시하거나 답변 근거 사용을 제한한다. 사용자 편집 요약을 자동 재생성하지 않는다.
- 기존 회의에 버전 정보가 없으면 레거시/판정 불가로 다루고 백필 경로를 제공한다.
- **완료:** ‘100만원→200만원’ 수정과 모두 바꾸기 모두 최신 검색에 반영되고,
  갱신 실패/종료/연속 편집 후에도 최신 버전으로 복구된다. 원본과 수동 요약은 보존된다.

### IMP-03 — Wiki 질문 범위

- 대상: `core/wiki/chat_integration.py`, `api/routers/search_chat.py`.
- 1차는 회의·날짜·화자 범위가 있는 질문을 기존 RAG로 보내 명확하게 보호한다.
  범위 없는 Wiki/BOTH와 router 비활성 동작은 유지한다.
- Wiki의 회의별 citation 필터링은 후속 선택 항목이다. 여러 회의 내용을 합성한
  페이지에서 citation 하나만 남기는 것으로 전체 본문을 해당 회의의 근거로 간주하지 않는다.
- **완료:** WIKI/BOTH 후보 질문에 개별·복합 필터를 적용해 다른 회의/날짜/화자
  근거가 혼입되지 않는다. 기본 RAG와 범위 없는 Wiki도 회귀 없이 동작한다.

### IMP-04 — 날짜의 의미와 재색인 보존

- 대상: `core/pipeline.py`, `core/reindex_recovery.py`, 회의 메타데이터.
- 실제 회의일, 파일 시각, 등록 시각, 재색인 시각을 구분한다. 최초 결정한 회의
  날짜와 출처를 저장하고 이후 인덱싱은 같은 값을 사용한다.
- 파일명 패턴·검증된 입력 시각·기존 메타데이터의 우선순위를 공통 계약으로 만든다.
  근거가 충돌하는 과거 회의를 오늘 날짜나 DB created_at으로 자동 확정하지 않는다.
- **완료:** 일반 파일명/날짜 파일명/원본 부재/출처 충돌/자정 경계에서 재색인 전후
  확정 날짜가 보존된다. 미확정 회의는 그 상태가 명시되고 원본은 바뀌지 않는다.

### IMP-05 — 화자 검색 저장·질의 계약

- 대상: `steps/embedder.py`, `search/hybrid_search.py`, 관련 인덱스 migration.
- 지원 범위 안의 실제 Chroma에서 현재 writer/query를 재현한다. metadata 연산자가
  지원되는지와 저장한 타입에 적용 가능한지를 별도로 확인한다.
- 우선 기존 의존성 범위에서 가능한 일관된 저장·필터 방식을 선택한다. 배열 metadata를
  채택하려면 최소 버전·기존 CSV 이행·호환 reader를 함께 결정한다.
- 화자 식별자를 부분 문자열로 잘못 매칭하지 않는다. 벡터 오류는 무조건 빈 결과로
  숨기지 않고 소스별 검색 장애와 검색 결과 없음의 차이를 전달한다.
- **완료:** 한 명/여러 명/UNKNOWN/없는 화자/비슷한 식별자에서 벡터와 FTS의 범위가
  일치한다. 단어가 같지 않아도 의미 검색이 살아 있으며 구형 인덱스 이행이 검증된다.

### IMP-06 — 검색 진단과 복구

- 대상: `api/routers/reindex.py`, 검색 storage helper, `ui/web/settings-view.js`.
- 원문 버전, 기대 청크 집합, Chroma·FTS 반영 상태를 함께 확인한다. 청크 1개 존재나
  양쪽 개수가 같다는 이유만으로 완전성을 확정하지 않는다.
- 빠른 상태 확인과 상세 무결성 검사를 구분해 매번 모든 본문을 읽지 않도록 한다.
- 누락/부분/오래됨/점검 불가를 구분하고 복구 가능한 대상에 단건·전체 복구를 제공한다.
- 복구는 기존 순차 큐와 회의 잠금을 사용한다. 재전사·삭제·편집과 경쟁 시 데이터
  보존과 작업 순서를 지킨다. 실패를 성공으로 표시하거나 원문을 삭제하지 않는다.
- **완료:** FTS-only 유실, 일부 벡터, 서로 다른 청크 ID, 오래된 버전, 저장소 접근
  실패를 구분한다. 복구 후 두 저장소가 같은 최신 원문을 가리키고 실패 시 재시도 가능하다.

## 7. 변경·복구 원칙

- 데이터 변경은 기존 회의별 coordinator, no-follow/pinned writer, no-replace
  보존 규칙 안에서 수행한다. 새 기능을 위해 보호를 제거하지 않는다.
- metadata 변경은 추가 가능한 schema부터 시작하고 과거 회의는 근거 있는 값만
  채운다. source/인덱스 버전과 복구 상태가 없는 기존 데이터도 읽기 가능해야 한다.
- 인덱스 migration은 합성 fixture→격리 복사본→명시적 실행 순서로 검증한다.
  실제 사용자 저장소의 일괄 삭제/재생성은 계획서 승인만으로 자동 실행하지 않는다.
- rollback은 원문 보존과 호환 읽기를 우선한다. schema를 지우는 down migration을
  기본 복구로 삼지 않는다. 새 형식이 구버전과 호환되지 않으면 안전한 forward fix
  또는 검증된 백업의 격리 복원을 선택한다.
- 설정·API/UI 계약이 바뀌면 해당 구현 작업에서 README/AGENTS/STATUS 등 관련 문서를
  갱신한다. 과거 완료 계획의 설명을 현재 미구현 기능처럼 재사용하지 않는다.
- production 의존성, 인증 기본 정책, 데이터 삭제, 외부 업로드/게시/서명·배포 작업은
  실제 실행 범위가 구체화되는 시점에 기존 사용자 승인 범위와 프로젝트 지침을 확인한다.
  지금은 그 작업을 실행하거나 포괄 승인받은 것으로 취급하지 않는다.
