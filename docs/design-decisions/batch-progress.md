# 일괄 처리 선택·접수·단계 표시

기준: 2026-09-08, `Aura/batch-progress-ux` 로컬 변경.

## 판단과 범위

외부 사용 사례의 ‘2건 실행’은 우리 서비스의 장애 이력으로 취급하지 않는다.
이번 변경은 선택한 회의와 실행 버튼의 거리, 실행 범위 확인, 접수 기록 부족,
전사 성공과 후처리 실패가 구분되지 않는 제품 동작을 대상으로 한다.

회의 목록에서 체크하면 바로 위에 선택 건수와 `전사만`, `전사 + 교정·요약`,
`교정·요약` 버튼을 표시한다. 상단의 기존 작업 버튼도 같은 확인 흐름을 사용한다.
최근 24시간은 녹음 시각이 아닌 DB `created_at`, 즉 **앱 등록 시각** 기준이다.

## 실행 계약

- `POST /api/meetings/batch/review`: 후보별 상태, 실행 가능 여부, 제외 이유,
  오디오 검증 실패를 반환한다. 파일 하나가 잘못되어도 나머지 후보를 확인할 수 있다.
- 기존 `POST /api/meetings/batch/preview`는 엄격한 검증 계약을 유지한다.
- UI는 확인 목록에서 선택·해제한 ID를 `scope=selected`로 고정해서 제출한다.
  실행 직전에 새 회의가 생겨도 사용자 선택에 자동 추가하지 않는다. 요청당 최대 500건이다.
- 선택된 파일 중 검증 실패가 있으면 실행 버튼을 막는다. 사용자는 해당 파일을
  해제할 수 있다. 확인 후 실제 접수 사이에 오디오가 바뀌어 검증이 실패하면
  회의 ID와 전체 무접수 사유를 안내하고, 일부 전사만 큐에 넣지 않는다.
- DB 전사 큐 변경과 접수 내역 저장은 같은 SQLite transaction이다. 요청 ID를
  재전송하면 기존 결과를 반환하며, 같은 ID로 다른 payload를 보내면 409를 반환한다.
- 접수 응답은 ‘처리 완료’가 아닌 `N건 대기열 등록`이다. 선택 건수, 등록 건수,
  제외 건수와 회의별 결과가 기록된다. `requested_action`으로 전사만/전체 의도를 고정한다.
- `GET /api/batch-requests` 및 목록의 ‘접수 내역’에서 최근 30개 요청을 조회한다.
  과거 개별 작업의 실패 기록을 이후 개별 재시도의 완료 이벤트로 바꾸지 않는다.
  취소·입력 검증 보류도 기록하며, 웹소켓을 열지 않아도 기록한다.
- 별도 교정·요약은 기존 프로세스 내 순차 task를 사용한다. 앱 재시작으로 해당
  task가 사라지면 접수 내역에 중단과 재접수 필요를 표시한다. 자동 재개 가능한
  영속 LLM 작업 큐로 전환한 것은 아니다.

## 상태와 복구

`core/meeting_progress.py`가 완료 단계와 실패 단계를 공통으로 해석한다.
목록·상세·일괄 확인·실행 내역은 이 표시를 사용한다.

- 병합까지 완료한 교정 실패: **전사 완료 · AI 교정 실패**, **교정 재시도**.
- 음성 인식 후 화자분리 실패: **음성 인식 완료 · 화자분리 실패**.
- 교정을 건너뛴 완료: **전사 완료 · 교정·요약 대기**.
- 저장된 병합 전사문은 후처리 실패에도 열 수 있다. 진행 중에도 이미 저장한
  전사문을 읽을 수 있으며 상세 화면은 상태를 계속 갱신한다.
- 전체 작업의 재시도는 기존 체크포인트에서 재개한다. 전사만 완료한 DB row의
  별도 LLM 실패는 상태 파일을 반영해 표시하고, 재시도는 STT 큐 대신 LLM 경로로 보낸다.
- 기존 부분 산출물의 안전한 복구 여부를 확인할 수 없는 경우에는 보존·차단하는
  기존 정책이 유지된다. 재시도 버튼이 모든 파일 충돌을 자동 해결한다는 뜻은 아니다.

## Gemma 로딩 오류

`per_layer_model_projection.biases/scales`의 ‘not in model’ 오류는 양자화
가중치와 모델의 projection 구현 불일치에서 재현할 수 있다. 설치된
`mlx-vlm 0.6.17`의 작은 Gemma 4 모델로 양자화 projection의 strict 로딩과
forward를 검증했다. 기존 production 의존성의 하한을 이 버전으로 올리고,
해당 오류에는 패키지 업데이트 또는 교정 모델 변경 후 재시도를 안내한다.

예상하지 못한 가중치를 삭제하거나 strict 검증을 우회하지 않는다. 외부 제보자의
설치 버전·모델 캐시는 확인하지 않았으며 실제 E4B 전체 모델 추론 검증도 별개다.

## 실행 순서 비교

| 항목 | 현재: 회의별 전사→교정·요약 | 전사 전체→교정·요약 전체 |
|---|---|---|
| 첫 회의의 완성된 요약 | 먼저 확인 가능 | 전체 전사가 끝날 때까지 지연 |
| 모든 회의의 전사문 확보 | 중간에 회의별 LLM 시간이 들어감 | 전사문 확보를 우선함 |
| 모델 교체 | 회의별로 STT/LLM 교체 | LLM을 유지하면 교체 비용 감소 가능 |
| 실패 영향 | 한 회의 실패 후 다음 회의 계속 | LLM 오류여도 모든 전사문 확보 가능 |
| 추가 설계 | 기존 순차 worker 유지 | 단계별 영속 큐, 재시작 복구, 취소·쿨다운 필요 |

현재 `run_llm_steps()`는 회의마다 모델을 해제한다. 따라서 호출 순서를 모으는
것만으로 Gemma를 한 번 로드해 재사용하지 않는다. 또한 로컬 전사는 화자분리
모델과 번갈아 실행되므로, ‘전사 먼저’가 STT 모델 한 번 로드를 보장하지 않는다.
모델을 장시간 유지하려면 한 번에 한 대형 모델·메모리 상한·서멀 관리 계약까지
검증해야 한다. 이번 변경은 실행 순서를 유지하며, 두 단계로 쓰려면 우선
`전사만`을 완료하고 같은 회의를 선택해 `교정·요약`을 실행한다.

## 재현 가능한 검증

```bash
.venv/bin/python -m pytest tests/test_batch_history.py tests/test_routes_meetings_batch.py -q
.venv/bin/python -m pytest -m e2e tests/test_e2e_batch_progress.py -q
.venv/bin/python -m pytest -m native tests/test_mlx_client.py -q
```

브라우저 E2E는 격리한 서버에 35초 WAV 13개 및 제외 사례 3개를 등록한다.
후보 16건 → 선택 14건 → 접수 12건·제외 2건 → 교정 실패 2건·완료 10건을
실제 UI/API/SQLite/worker로 대조한다. 실패 후에도 다음 작업 실행, 페이지를
새로 연 뒤 접수 조회, 전사문 열기, 교정 재시도 시 STT 호출 수와 병합 파일
SHA-256 보존을 검증한다. 별도 전사만→교정 실패→교정 재시도도 검증한다.
화면 검증은 데스크톱과 모바일 크기를 포함한다.

음성 인식·화자분리·교정·요약·임베딩의 모델 호출은 테스트 대역이다.
오디오 변환·병합·체크포인트·큐·재개는 실제 코드다. 이 검증을 실제 음성
인식 품질, 전체 Gemma 모델 호환성, 외부 서비스 장애의 재현으로 해석하지 않는다.
