# 일괄 작업과 백그라운드 제목 정리

## 사용자 문제

선택한 회의의 작업이 목록과 콘텐츠 상단에 중복 표시되고, 현재 열린 회의와
체크한 회의가 비슷한 색으로 보였다. 제목 생성은 모델을 기다리는 동안 모달을
유지하고 다시 적용해야 했으며, 여러 회의에 반복하기 어려웠다.

## 화면 계약

- 목록 위 한 곳에서 선택 수 → 작업 선택 → 실행 순서로 일괄 작업을 시작한다.
  현재 열린 회의와 체크한 회의의 시각 표시는 구분한다.
- `제목 자동 정리`는 개별·일괄 모두 같은 백그라운드 API를 사용한다. 생성 모달이나
  적용 버튼 없이 접수하고, 완료 시 날짜를 포함한 제목을 자동 저장한다.
- 전사·교정·요약의 기존 대상 확인과 외부 전송 동의 경계는 유지한다.
- 접수 직후 작업 내역 창을 강제로 열지 않는다. 화면 이동을 막지 않는 상태 표시와
  `작업 내역`에서 대기·실행·완료·실패·중단을 확인한다. 실패·중단 항목은 다시 실행할 수 있다.
- 제목 작업은 중단할 수 있고, 완료한 제목은 작업 내역에서 이전 값으로 복원할 수 있다.
  사용자가 이후 직접 수정한 제목은 복원 대상에서 제외한다.
- 개별 녹취의 드문 작업과 삭제·재전사는 `더 보기`로 모아 기본 화면의 밀도를 낮춘다.

## 서버 계약

`POST /api/meetings/titles`는 `meeting_ids`(최대 500개)와 `request_id`를 받는다.
동일 요청의 재전송은 한 번만 접수하며, 다른 내용으로 같은 ID를 쓰면 거부한다.
제목 요청도 기존 SQLite 접수·이벤트 기록에 남겨 `GET /api/batch-requests`로 조회한다.
브라우저가 닫혀도 서버가 실행 중이면 계속 처리한다.

서버의 단일 제목 작업자가 회의를 순차 처리하고 기존 모델 매니저를 사용한다.
회의별 변경 잠금 안에서 원문을 읽고 생성·저장하며, 접수 후 수동 제목 변경이나
대상 교체가 발견되면 자동 적용을 건너뛴다. 제목 변경과 완료 이벤트는 같은 DB
트랜잭션으로 저장한다. 한 회의 실패는 뒤의 회의를 중단시키지 않는다.

`POST /api/title-jobs/{request_id}/cancel`은 아직 적용하지 않은 항목의 저장을 막는다.
이미 시작한 native 연산은 안전하게 종료될 때까지 모델을 유지하지만 결과는 적용하지
않는다. `POST /api/title-jobs/{request_id}/undo`는 저장 이후 변경되지 않은 제목만
조건부 복원한다. 원본 파일명과 전사 내용은 변경하지 않는다.

앱 재시작 후 사라진 실행은 `중단`으로 표시한다. 오래된 입력·제목을 자동으로
다시 덮어쓰지 않도록 사용자가 작업 내역에서 재실행한다. 원래 `title-suggestion`
API는 호환성을 위해 미리보기 전용으로 유지한다.

## 검증 범위

- DB/API: 즉시 접수, 순차 처리, 중복 방지, 수동 수정 우선, 부분 실패,
  중단 후 늦은 저장 방지, 조건부 되돌리기, 재시작 내역.
- 브라우저: 개별·일괄 같은 경로, 화면 이동/새로고침 후 진행 확인, 실패 재시도,
  제목 목록 갱신, 단일 도구 모음, 키보드·접근성·좁은 화면.
- 모델 호출을 대역으로 바꾼 테스트와 실제 Gemma 실행 결과는 구분해 보고한다.

### 실제 모델 확인 (2026-09-23)

임시 데이터 폴더와 짧은 합성 전사문 두 건으로 실제 앱 API → 백그라운드 작업자 →
Gemma 4 E4B → SQLite 저장 경로를 실행했다. 기존 로컬 모델 캐시만 사용했고,
접수 응답은 약 0.02초, 두 제목 생성·저장은 총 21.05초였다. 녹취일을 각각 붙인
제목 두 개를 생성한 뒤 이전 제목 두 개를 복원했다. 원본 파일·체크포인트 hash는
같았고 종료 시 모델 로드와 native 정리 대기는 모두 해제됐다.

이는 짧은 입력 두 건의 기능 검증이다. 실제 사용자 녹취나 대규모 처리 속도·
제목 품질을 대표하지 않는다. 화면 이동·새로고침·수동 제목 수정 우선은 실제
브라우저·API·SQLite를 연결하고 모델 응답만 대역으로 바꾼 E2E에서 별도로 검증한다.
