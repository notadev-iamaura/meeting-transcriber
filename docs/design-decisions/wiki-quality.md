# Wiki 근거 검수와 사용자 수정본 보존

기준일: 2026-11-06

Recap의 Wiki는 회의에서 나온 지식을 로컬 Markdown으로 축적한다. 인용 위치의
존재, 주장과 인용의 내용 일치, AI 자체 평가, 사용자의 검토는 서로 다른 정보다.
AI의 자체 평가 점수는 정답률이나 사용자의 승인으로 표시하지 않는다.

## 원문 교정의 실패 추적과 재시도

- 교정 실패는 집계뿐 아니라 발화 위치·사유·원문 결합 해시를 `correction_failures`에
  보존한다. 해시는 원문·화자·시각을 함께 묶는다. 개별 기록과 집계가 맞지 않거나
  이미 수정된 발화면 재시도를 거부한다. 과거 체크포인트에 개별 기록이 없으면
  별도 감사로 대상을 복원해야 하며, 같은 문장이라는 이유로 실패 위치를 추정하지 않는다.
- 재시도는 확인된 실패 묶음만 더 작은 배치로 한 번씩 요청한다. 기존 성공 발화와
  화자·시각을 유지하고, 누락·문장 이동·병합·과도한 축약·확장은 다시 거부한다.
  `retry_failed()`는 새 결과를 반환할 뿐 체크포인트를 직접 덮어쓰지 않는다. 저장하는
  호출자는 원본 SHA·사용자 편집 상태를 다시 확인하고 회의별 mutation lease 안에서
  회의록·검색 등 후속 산출물을 갱신해야 한다.
- 수치·부호·소수점·비율·숫자 순서와 부정 표현의 변화를 보수적으로 검사한다.
  명확한 천 단위 쉼표나 백분율의 동등 표기만 정규화하며, 문법 검사 통과를
  고유명사·단위·문장 전체 의미 보존의 증명으로 삼지 않는다. 재추론 통과와 별도의
  원문 대조를 구분하고, 불확실한 후보는 원문과 실패 사유를 유지한다.

## 자동 생성과 근거 검사

- 기존 인용 형식·발화 존재·자체 평가 검사를 유지한다.
- 프로덕션 Wiki 컴파일러는 기본으로 `LocalClaimGrounder`를 연결한다. 실제 인용한
  발화와 각각의 주장을 기존 로컬 LLM으로 다시 대조한다. 외부 API나 새 모델을
  추가하지 않는다.
- 모든 주장 ID의 판정과 실제 발화에서 그대로 가져온 근거 문구가 있어야 통과한다.
  숫자·담당자·부정·제안과 확정의 차이를 검사하도록 지시한다. 별도 검수 추론도
  완전한 사실 보증은 아니며, 실제 회의 품질은 사람 정답과 별도로 비교해야 한다.
- 근거에는 회의별 화자 ID와 실제 시작·종료 시각을 함께 제공한다. 같은 초에 나온
  발화도 화자별 구간을 보존하고, 근거 문구는 한 발화 안의 연속된 원문이어야 한다.
  요청 대상·조건부 지원 제안자·업무 수행을 약속한 사람을 구분하며, 발화했다는
  이유만으로 업무 담당자로 인정하지 않는다. 연결되지 않은 주변 발화를 검수 근거로
  자동 확장하지 않는다.
- 번호형 근거 선택(witness)의 긍정 응답은 `{id, verdict, evidence_index, segment_index}`다.
  두 index는 현재 claim의 `evidence`와 선택한 `segments` 배열 안의 0부터 시작하는
  정수 위치여야 한다. bool·문자열·실수·음수·범위 밖 값은 거부하며, 다른 claim의
  배열이나 전역 순번으로 해석하지 않는다. `segments`가 없는 근거는 `segment_index: 0`으로
  그 `evidence.text`만 선택한다.
- 번호형에서는 모델이 quote를 다시 쓰지 않고 서버가 선택된 원문 항목 하나를 그대로
  복사한다. 선택한 segment 또는 evidence만 화자·역할·종료 검수에 넘기며, 잘못 고른
  화자를 다른 출처의 같은 문장으로 구제하지 않는다. 대표 발화 선택과 별개로 연결된
  전체 근거의 업무 범위·조건을 대조할 의무는 유지한다.
- 기존 `{id, verdict, quote}` 응답도 원문 포함 검사와 화자·역할·종료 검수를 그대로
  적용한다. `{id, verdict}`만 있는 응답은 `contradicted`·`insufficient`의 의미 보류에만
  허용하며 근거 검증 성공을 뜻하지 않는다. `supported`는 유효한 번호형 근거 또는
  기존 quote가 반드시 필요하고, 긍정 판정만으로 근거를 생략할 수 없다.
- 원 batch의 판정·ID·형식을 먼저 확인하고 반대·불충분 판정이 하나라도 있으면 번호 수리를
  호출하지 않는다. `supported`의 잘못된 근거 번호만 문서당 최대 한 번 별도로 선택하며,
  응답은 해당 ID와 실제 유효한 두 index 또는 명시적 null만 허용한다. 기존 판정·정상 행·
  원문은 보존하고 번호 수리 뒤에도 원문·화자·역할·종료 검사를 다시 통과해야 한다.
  `max_reference_repairs: 0`은 이 수리를 끄며, 1을 넘길 수 없다. 의미 판정의 재시도나
  범위 밖 번호의 자동 보정은 하지 않고 기존 문서 전체 시간·입출력 예산을 공유한다.
- 질문·요청을 담은 quote로 합의·확정 약속을 입증하지 않는다. 명시된 임시 화자
  담당자와 실제 quote 구간의 화자가 다르고 직접적인 배정 근거도 없으면 보류한다.
  요청했다는 사실을 요청으로 기록한 문장과 실제 실행 약속은 구분한다. 이 문법
  보호와 로컬 모델 판정이 한국어 전체의 의미 정확성을 보증하지는 않는다.
- 결정 제목도 별도의 주장으로 검수한다. 결정 내용에 달린 실제 인용을 우선 사용하며
  제목 자체의 인용을 새 근거로 가져오지 않는다. 현재 상태 보고를 새 확정 결정으로
  바꾸거나, 복합 주장 중 일부만 맞는 것을 전체 지지로 처리하지 않도록 대조한다.
- 근거 불일치, 검수 실패·시간 초과, 입력 예산 초과는 `pending/`에 검토 후보로
  보존한다. 기존 공개본은 유지하며 보류 이유를 기록한다. 후보 충돌도 기존 내용을
  조용히 덮어쓰지 않도록 보존한다.
- 취소는 작업 취소로 전달한다. 검수에 실패한 내용을 성공한 것으로 게시하지 않는다.
- 결정의 본문·배경·후속 액션은 각각 실제 입력 인용이 필요하다. 다른 필드의 인용이나
  첫 발화를 누락 필드에 복사하지 않으며, 입력에 없는 0초를 첫 발화 시각으로 바꾸지 않는다.
  실제 입력에 제공된 0초 마커는 정상 인용으로 유지한다.
- 새 결정 문서에서 추출된 배경이나 후속 액션이 비어 있으면 `미확인`으로 표시한다.
  이는 실제 배경·후속 업무가 없다는 판단이 아니다. 정확한 placeholder 한 줄만 인용에서
  면제하며, `후속 업무 없음`·`담당자 미확인` 같은 실제 주장은 계속 인용을 요구한다.
- 결정의 `participants`는 모델이 고른 이름 대신 입력 발화에 실제로 있는 비어 있지 않은
  화자 라벨 전체를 정렬·중복 제거해 채운다. 제공된 실명 라벨과 `UNKNOWN`은 유지하며,
  이 목록은 개별 결정에 대한 동의나 실명·신원을 검증한 명단을 뜻하지 않는다.
  기존 사용자 편집본은 기존 보호 경로를 유지한다.
- 결정의 누락·잘못된 인용은 회의당 한 번 묶어서 복구를 시도한다. 모델에는 원문 재작성
  대신 주장 번호와 실제 전체 인용 마커의 매핑만 요청하고, 입력에 제공한 정확한
  마커 집합에 속하는지 확인한다. 질문·확답이 함께 필요하면 복수 인용을 허용한다.
  이 존재 검사를 통과해도 기존 내용 일치·신뢰도 Guard를 다시 거쳐야 한다.
- 프로젝트 문서는 문서당 한 번만 같은 예산으로 누락 마커를 복구한다. 본문·기존
  인용·공백을 보존하며 실제 입력 마커만 덧붙인다. 부분 복구는 미해결 표시를 유지하고,
  원래 미해결 메타데이터가 없어도 복구 결과에 누락이 남으면 D1 삭제 전에 본문을
  pending에 보존한다. 전부 복구해도 기존 Guard를 거쳐야 한다.
  `grounding.enabled: false`이면 이 추가 요청을 하지 않는다. 문서당 상한을 회의 전체의
  모델 호출 상한으로 해석하지 않는다.
- 전체 발화가 복구 입력 예산에 들어가면 그대로 사용한다. 긴 회의는 주장별 한글
  문자 ngram·토큰 유사도로 관련 발화를 고르게 찾고, 바로 앞뒤 실제 대화 턴을
  추가한다. 발화 중간을 자르거나 문장을 새로 만들지 않으며 원래 순서로 구성한다.
  복구 응답의 인용도 이때 실제 선택한 입력 마커 집합 안에 있어야 한다.
- 인용 복구는 기존 `wiki.grounding`의 주장 수·항목·입출력·시간 예산을 재사용한다.
  실패·예산 초과·누락 지속은 `citation_unresolved` 사유로 D1 본문 삭제 전에
  pending에 원문을 보존하며 기존 공개본은 유지한다. 검토 후보를 수정·검토하는
  것만으로 자동 게시하지 않는다. 명시적 취소는 복구 성공이나 보류 완료로 삼키지 않는다.
- `WikiGuard`를 직접 사용하는 과거 테스트·임베딩 호출자는 선택적으로 검수기를
  주입한다. 프로덕션 연결은 `steps/wiki_compiler.py`가 담당한다.

실행 예산은 `config.yaml`의 `wiki.grounding`에서 관리한다:

```yaml
wiki:
  grounding:
    enabled: true
    batch_size: 6
    max_claims: 48
    max_input_chars: 24000
    max_item_chars: 6000
    max_output_tokens: 2048
    max_reference_repairs: 1
    timeout_seconds: 120
```

검수는 추가 로컬 추론을 사용하므로 Wiki 생성 시간이 늘어난다. 발화 일부를
잘라서 완전한 근거처럼 처리하지 않는다. 여러 발화에 걸친 주장은 각각을 인용해야
하며, 예산을 넘는 문서는 보류한다. `enabled: false`는 기존 존재 검사만 적용하는
호환 경로이므로 내용 일치를 검사했다고 해석하면 안 된다. Wiki 자체의 활성화와
`dry_run` 기본값은 이 설정과 별개다.

## 누적된 프로젝트와 현황

- 기존 프로젝트의 frontmatter, 타임라인, 미해결 이슈를 실제 원문에서 읽는다.
  갱신 과정에서 모델이 이전 이력을 생략해도 그대로 보존한다.
- 프로젝트 상태는 별도의 명시적 전환 근거가 있을 때 갱신한다. 오래된 회의가
  최신 상태를 되돌리지 않게 하며, 날짜를 확정할 수 없는 갱신도 보수적으로 처리한다.
- 담당자·착수일·목표일은 구조화된 추출값과 유효한 기존 값만 사용한다. 렌더 모델이
  새로 만든 값은 버리고, 확인할 값이 없으면 필드를 생략한다. 기존 착수 이력은
  보존하며, 익명 화자 라벨을 회의 간 인물이나 담당자 이름으로 연결하지 않는다.
- 현황의 임시 화자 담당자도 단일 출처 회의 안에서만 묶는다. 회의가 불분명하거나
  여러 회의에 걸친 항목과 `UNKNOWN`·미지정 담당자는 항목별 확인 필요로 나눈다.
  API와 화면 및 파생 Markdown에 같은 회의 범위를 표시하며, 원래 업무·담당자 ID·
  인용·상태는 보존한다. 명시된 실명 담당자는 기존 정확 일치 그룹 정책을 유지한다.
- 실제 프로젝트 메타데이터 값도 본문과 별도의 주장으로 검수한다. 메타데이터 자체는
  근거가 아니며 본문에 실제 달린 인용 발화를 사용한다. 회의 날짜에서 착수일을,
  이름 언급에서 담당자를 추정하지 않는다. 질문·조건부를 확정으로 바꾸지 않으며,
  질문과 확답이 함께 필요한 주장은 양쪽의 정확한 인용을 사용한다.
- 실제 프로젝트 상태 네 가지(`in-progress`, `blocked`, `shipped`, `cancelled`)도
  프로젝트 이름·작업 범위와 묶어 별도로 검수한다. 가능 여부를 확인하는 작업의
  진행을 전체 구현의 진행·완료로 확대하지 않는다. 프로젝트 자체가 확인 작업이면
  그 범위의 진행은 인정할 수 있다. `pending`·`unknown` 같은 검토용 상태는 회의
  사실로 평가하지 않는다.
- 현황의 현재 결정에는 확정된 결정만 포함한다. 제안·검토 필요·거부·대체된 결정은
  현재 상태로 승격하지 않으며 원본 기록은 보존한다.
- `현재 확정된 결정`을 명시적으로 요청하는 표현은 Wiki 경로로 분류한다. 정확한
  발언 인용도 함께 요청하면 기존 BOTH 우선순위를 유지하며, 미확정·검토 중·미래
  표현을 이 새 신호로 인정하지 않는다.
- 따옴표로 하나의 주제를 명시한 질문에서는 각 공개 결정의 현재 제목·본문에 주제
  단어가 모두 있는지 확인한다. 오래된 색인 발췌·숨김 주석·인용 식별자는 주제 일치
  근거로 쓰지 않으며, 일치하는 공개 결정이 없으면 원문 RAG로 전환한다. 따옴표 없는
  일반 질문과 여러 주제를 각각 따옴표로 표시한 비교 질문은 기존 검색 동작을 유지하며,
  이 검사가 모든 자연어 질문의 의미상 관련성을 보증하지는 않는다.
- 같은 업무·담당자·기한·프로젝트·발화 인용이 모두 같은 액션은 재검수해도 중복하지
  않는다. 완료된 업무의 원래 회의를 다시 처리해도 같은 출처의 업무를 다시 열지
  않으며, 종료 이벤트 전체가 같을 때만 완료 이력을 합친다. 내용이나 출처가 다른
  업무는 과거 ID가 같더라도 별도로 보존한다.
- 원래 담당자·기한·프로젝트·항목 ID·알려진 출처 날짜와 종료 사유를 버전이 있는
  숨김 주석에 보존한다. 표시 줄의 SHA와 메타데이터 체크섬을 검사하며 손상되면
  기존 문서 갱신을 중단한다. 주석 없는 과거 Closed의 담당자·기한은 추정하지
  않고, 그 기록과 같은 출처의 새 추출로 재개방하지도 않는다. 이미 존재하는 다른
  Open은 보존한다. 체크섬은 우발적 손상 검사이며 같은 사용자 권한의 변조를
  인증하는 수단은 아니다. 읽기·수정 화면에는 저장용 주석을 표시하지 않는다.
- 주 인용은 기존 업무 식별 근거로 유지하고 추가 근거는 `supporting_citations`로
  순서대로 보존한다. 질문·요청과 수행 약속이 다른 발화에 있으면 함께 인용할 수
  있다. Closed의 원래 업무 인용도 보존하며 종료 보고의 단일 인용과 구분한다.
  보충 인용을 더했다는 이유로 별개 업무를 만들지 않는다.
- 종료 주장은 원래 업무의 전체 범위·종료 사유·보고자를 실제 종료 발화로 별도
  검수한다. 질문·요청·미래 약속·진행 중·단순 맞장구만으로 완료를 인정하지 않는다.
  과거 종료 사유를 알 수 없는 경우에는 추정하지 않고 자동 갱신을 보류한다.
- 새 기한은 실제 단일 인용 발화의 명시 날짜 또는 상대 날짜에서만 정한다. 다른
  업무 날짜나 임의 첫 발화의 날짜를 가져오지 않으며, 날짜가 여러 개이거나 해당
  발화를 정할 수 없으면 미정으로 남긴다. 기존에 알려진 기한은 그대로 보존한다.
- 서로 다른 두 결정을 AI가 임의로 동일시해 `supersedes` 관계를 확정하지 않는다.
  자동 모순 탐지 또는 결정 관계 전체가 해결된 것으로 해석하지 않는다.

## 답변 문장과 인용의 연결

- Wiki 답변은 현재 게시 문장의 기존 인용을 실제 교정 원문과 대조한다. 내용 없는
  군말·맞장구를 주 인용에서 제외하고, 확인 질문은 약속의 대상·조건을 설명하는
  보조 문맥으로 보존한다. 같은 게시 문장에 이미 붙은 인용 사이의 토큰 순위는
  직접 발화를 앞에 두기 위한 수단이며, 주장 지지의 의미 증명이 아니다.
- 생성한 사실 문장은 같은 주 인용에 연결된 현재 게시 문장과 내용이 같아야 한다.
  목록·공백·문장 끝 표기만 정규화하고 수치·부호·소수점 등 내용상의 기호는 보존한다.
  유효한 인용이 있다는 이유만으로 다른 문장·주체·금액·완료 주장을 허용하지 않는다.
  의역을 의미 오류로 단정하지는 않지만 연결을 확인할 수 없으면 게시 문장을 그대로
  반환한다. 인용이 없는 추가 사실이나 다른 문장의 인용 상속도 같은 경로로 처리한다.
- 기존 자유생성 RAG 경로에서 결정 질문에 확인 질문만 인용한 답변이 나오면, 그 질문만으로
  결정·담당자·완료를 확정할 수 없다고 밝힌다. 인용문이 같은 검색 구간의 동일 화자
  발언에 유일하게 연결될 때만 다음 화자의 발언을 원문 그대로 덧붙인다. 다른 회의나
  검색 결과에서 답변을 빌리지 않으며, 응답이 없거나 질문·맞장구뿐이면 미확인으로
  남긴다. 인접했다는 사실만으로 전체 업무의 확정·완료를 인정하지 않는다.
- 질문 자체를 찾는 요청과 이미 설명을 갖춘 답변은 유지한다. 이 보완은 일반 RAG
  답변 전체를 의미 검증하는 장치가 아니다. 스트림은 기존 토큰을 고치지 않고 보충
  문맥만 추가하며 최종 본문·세션 이력을 일치시킨다. 보충 토큰 전송 중 원문이
  수정돼도 이전 근거의 답변을 새 이력으로 저장하지 않는다.
- 기본 원문 RAG의 결정·상태·담당·원인·후속 질문과 원문 인용 요청은 생성 모델이
  현재 원문 후보의 번호만 선택한다. 출력은 실제 발언·화자·시각·인용을 코드가
  구성하며, 모델이 만든 설명·수신인·주체·완료 주장을 표시하지 않는다. 번호·형식이
  잘못되면 확인한 원문 일부와 제한된 범위의 안내만 반환한다. 이는 선택의 의미상
  관련성이나 전체 업무 상태의 정답률을 보증하는 검사는 아니다.
  전체를 감싼 단일 JSON 코드 블록만 문법적으로 벗길 수 있으며, 앞뒤 설명·여러 객체·
  잘린 JSON·추가 필드·중복·없는 번호·bool/null은 계속 거부한다. 실제 실행에서 확인된
  형식 거부와 의미상 빈 선택은 로그의 상태·개수로 구분하며 원시 응답은 일반 로그에 쓰지 않는다.
  선택 전용 system을 사용하고 자유생성용 사용자 문체 지시는 이 단계에 섞지 않는다.
  모델 입력의 선택 번호는 단순 질문의 `id` 또는 복합 질문 묶음의 `selectable_ids`이며
  회의 범위는 문자열로 구분한다. 실제 원문
  순서·시각·화자는 내부 인용 검증에 그대로 남긴다. 모든 첫 입력에 현재 질문에서
  실제 등장한 일반 확인 항목만 `requested_items`로 전달한다. 항목은 질문이며
  사실·완료 판정이 아니고, 이전 질문이나 후보의 단어로 새 항목을 만들지 않는다.
  복합 질문은 따옴표 밖 문장 경계와 실제 확인 표현으로 절·항목을 제공한다. 대상과
  채널은 별도 key이며 결과·성과 같은 명사를 조사 `과`로 임의 분리하지 않는다.
  모델은 모든 제공 key에 근거 번호 목록 또는 빈 목록을 배정한 `facets` 계획만
  반환한다. 항목별 배정은 선택 기록이며 의미상 완전성이나 완료 판정이 아니다.
  같은 절에 여러 사건이 있으면 인식한 확인 축 뒤의 명시 접속에서만 국소 초점을
  나눈다. 대상·채널처럼 함께 묶인 축은 같은 질문 명사구를 공유하고, 따옴표 속 주제명을
  새 확인 항목으로 오인하지 않는다. `local_focus`는 추론 문구가 아닌 정확한 질문
  범위이며 결과·성과 같은 명사의 일부를 잘라 만들지 않는다. 혼합된 실제 발언 하나가
  여러 요구를 뒷받침하면 같은 번호를 여러 항목에서 재사용하고 전체 인용에서는 한 번 센다.
  문두의 명시적 `…할 때`·`…인 경우` 조건 안의 설명 표현은 별도 답변 항목으로 만들지
  않고 뒤의 실제 요구를 따른다. 조건은 정확한 질문 초점에 남기고 OR나 명사형 대상·채널
  요구를 조건으로 바꾸지 않는다. 이 규칙은 일반적인 한국어 질문 의미 분석을 보장하지 않는다.
  첫 입력·보완 입력 마지막에는 실제 항목 key와 빈 ID 배열로 된 `response_template`를
  제공해 입력 메타데이터와 출력 구조를 구분한다. 메타데이터 복사·불완전 JSON은 계속
  거부하며, 빈 틀만 반환한 결과도 유용한 답변으로 세지 않는다.
  순수 맞장구는 모델 후보에서 제외한다. 회의 범위·원문 번호·raw 화자·문구로 입력을
  압축하고 질문·바로 다음 실제 응답은 완전한 묶음으로 넣어 질문만 남지 않게 한다.
  선택 질문의 연속된 다음 두 발언과 같은 화자의 앞뒤 미완결 연결절은 검색된 전체
  현재 후보에서만 입력·발언 수 예산 안의 `연결 문맥`으로 표시한다. parent가 달라도
  같은 회의의 실제 원문 번호가 연속되고 각자의 인용·시각이 확인된 때만 허용한다.
  대상이 생략된 짧은 답변은 바로 앞 다른 화자의 실제 연속 질문을 최대 두 개까지
  문맥으로 보존한다. `네트워크`를 `네` 응답으로 보지 않으며, 같은 화자의 `고요.`처럼
  ASR 마침표가 붙은 연결절도 원문을 바꾸지 않고 바로 다음 절과 묶는다.
  이 부드러운 연결은 정방향에만 적용한다. 역방향은 종속된 필수 선행절만 따르므로
  앞선 `고요.` 배경까지 연쇄적으로 붙여 필수 인용 예산을 잠식하지 않는다.
  완결된 앞 주장이나 건너뛴 발언을 임의로 추가하지 않는다. 답변과 개별 인용은 같은
  원문 순서로 구성해 질문·응답·후속 조건을 서로 다른 주체에게 옮기지 않는다.
  선택한 질문·요청 바로 다음의 실제 짧은 응답은 문맥 전용으로만 보존할 수 있다.
  맞장구를 단독 사실·모델 선택·합의·완료 판정에 쓰지 않으며, 현재 검색된 parent의
  실제 화자·시각·자기 참조와 최종 원문 재검사를 동일하게 적용한다.
  복합 질문의 출처 발행 단계에서만, 실제 모델이 선택한 같은 원질문자의 요청이 바로 앞 답을 이어 받는
  `그럼/그러면` 요청을 앞 QA와 묶을 수 있다. 같은 회의의 연속된 질문 1–2개·다른 화자의
  지시적 답·원질문자의 요청이 있고 실제 내용어가 겹칠 때만 허용한다. UNKNOWN·빈 화자를
  같은 인물의 증거로 쓰지 않고, 일반 확인·요청어만의 겹침이나 명시적 주제 전환·부정은
  새 join을 막는다. 다음 주 같은 일정 수식 자체를 주제 전환으로 간주하지 않는다.
  새 unit은 앞 QA·답·요청·직후 맞장구의 실제 문맥이며 수신인·합의·완료를 추론한 사실이 아니다.
  기존 두 단계 선택 모드에서는 이 추가 unit을 모델 입력·선택 비용·PACK·기본 선택 검사에 반영하지 않는다.
  검증된 기본 선택 경로를 유지하고, 선택이 끝난 뒤 initial current pool의 실제 원문 객체로만
  문맥을 추가한다. 원래 base 인용과 전체 unit 합집합이 8개와 실제 이스케이프 표시 길이
  상한에 통째로 들어갈 때만 발행한다. 공유 원문이 있는 활성 unit들은 함께 보존하거나
  요청 anchor를 포함해 전체 제외하고 제한을 표시한다. 새 모델 선택 번호·사실을 만들지 않는다.
  최종 추가 원문도 각자의 parent·raw 화자·시각·원문 신선도를 확인하며, 생성 뒤 새로 읽은
  Q를 옛 선택에 섞지 않는다. 최종 실제 모델 선택 anchor가 남은 때만 `llm_used`로 세고
  문맥 잔여만 남은 결과를 생성 성공으로 세지 않는다. 기본 정책이 꺼진 literal·no-reply
  경로와 다른 기존 문맥 규칙은 유지한다.
  기본 복합 질문은 실제 질문 초점을 나누어 같은 모델 lease에서 최대 4번 독립 선택한다.
  각 입력에는 전체 질문과 해당 초점, 원문 순서의 실제 발언과 필수 문답 문맥을 제공한다.
  초점의 원래 질문 절도 함께 전달해 명사를 찾는 요청과 완료 여부를 묻는 요청을
  구분한다. 문장 술어가 없는 조사·연결절은 같은 화자의 실제 다음 발언과 함께 읽고,
  다른 화자의 질문에 이어진 실질적인 답변은 문답 관계를 검색 단서로만 사용한다.
  종료 상태·범위를 명시적으로 묻는 초점은 종료 표현이 있는 실제 발언을, 검증 상태를 묻는 초점은 검증 보고나
  향후 검증 전망을 우선 후보로 제한한다. 두 축을 함께 묻는 초점에는 양쪽 후보를 유지한다.
  종료 질문·부정 보고도 원문 후보이며, 종료·검증이 완료됐다는 자동 판정은 아니다.
  검증 전망과 현재 관찰·정중한 요청을 구분하고, 종료 뒤 조건부 후속은 같은 화자의
  연속된 실제 문맥에서만 연결한다. 해당 후보가 없으면 제한을 표시한 기존 후보 경로를
  사용하며 자료 부재나 미완료를 추정하지 않는다.
  물리적인 창 닫기처럼 단어에 `닫`이 있다는 이유만으로 종료 상태 후보로 제한하지 않는다.
  검증 전용 선택 지시는 검증 상태 초점에만 적용한다. 일반 초점은 일반 지시를 쓰며,
  질문 전체의 입력 예산에는 실제 사용하는 지시 중 가장 긴 것을 예약한다.
  검증 초점은 완료를 긍정하는 증거만 고르는 작업이 아니다. 실제 관찰·예상·조건이
  확인 범위를 제한하는 경우에도 그 발언을 선택하도록 안내하며, 예상에서 검증 완료나
  자료 부재를 새로 추론하지 않는다.
  필요성과 처리 방식·방법을 함께 묻는 명시적 초점에는 실제 필요 근거와 처리 방식을
  함께 고르도록 안내한다. 인용된 프로젝트 이름이나 일반적인 `어떻게 구분`만으로는
  이 안내를 붙이지 않는다. 해당 초점에서만 같은 확인된 화자의 바로 다음 이유절을
  입력 순위와 이미 모델이 선택한 근거의 배분 순위 단서로 사용하며, 그 이유절을 자동 선택하거나 사실로 판정하지 않는다.
  기본 초점 선택 입력은 `evidence_units`에 실제 선택 번호와 전체 필수 문맥을 함께 둔다.
  카드는 초점 관련 순위로 표시하고 카드 안의 발언은 실제 원문 순서로 유지한다. 실제
  시각을 제공하며 여러 회의가 함께 있으면 카드별 회의 범위도 제공한다. 카드 순위를
  시간 순서나 마지막 상태로 해석하지 않는다.
  같은 전체 문맥만 합치고 일부만 겹치는 문맥은 각 카드에 온전히 남긴다. 각 카드에는
  해당 문맥 안에서 순위가 가장 높은 실제 원문 번호 하나만 선택 번호로 제공한다.
  나머지 발언은 문맥으로 모두 보존하되 선택 번호를 붙이지 않는다. 카드 안의 여러
  번호를 복사해 한도를 초과하는 문제를 줄이기 위한 입력 방식이며 기존 엄격한 번호
  파서의 개수·중복·자료형·없는 번호 검사는 완화하지 않는다. 모든 카드에 표시한
  문맥까지 원문 최신성 검사에 포함한다.
  카드 수 상한은 기존 전체 인용 상한과 초점별 선택 상한의 곱으로 제한한다. 기본은
  8×3=24개 카드이며 전체 JSON 길이도 카드 단위로 검사한다. 이 입력 카드 수와 최종
  답변의 원문 인용 상한 8개는 별개다.
  카드 후보를 줄일 때에는 질문과 실제 발언의 요청·확인 행위가 일치하는 경우에만
  같은 확인된 화자의 앞선 연속 발언에 있는 주제 이름을 순위 단서로 이어 받는다.
  이때 주제는 첫 주제 질문과 해당 초점·원래 질문 절에 공통으로 있는 실제 내용 단어로
  한정하며, 일반적인 자료·공유 표현만으로 별개 사안의 주제를 새로 만들지 않는다.
  다른 화자·발언 누락·미확인 화자·명시적 주제 전환에서 연결을 끊고 뒤의 주제를
  앞 발언에 소급하지 않는다. 문답 카드의 요청 문맥을 업무 담당자 배정으로 해석하지 않는다.
  명시적 주제가 없는 것으로 분류한 상태 초점에서는 첫 주제 질문과 원래 질문 절에
  공통으로 쓰인 실제 내용 단어도 카드 순위 단서로 사용한다. 별도 대상이 명시됐거나
  공통 주제가 없거나 인용된 이름만 겹치는 경우에는 이 단서를 적용하지 않는다.
  각 호출은 자신에게 표시된 정수 ID만 선택할 수 있으며, 다른 호출의 후보를 대신 선택하지 못한다.
  서버는 모델이 실제 선택한 번호만 대상으로 제한된 대안을 탐색한다. 포함된 초점 수와
  실제 주제·시간 표현, 선택 순위, 문맥 비용을 비교한 뒤 남은 예산에 추가 근거를 채운다.
  탐색 폭은 기존 인용 상한과 실제 초점 수로 제한하며 모든 조합의 최적해를 보장하지 않는다.
  모든 대안에서 필수 문맥 전체와 실제 이스케이프 표시 길이를 기준으로 전역 인용 예산을 검사한다. 제외·빈 선택은 제한으로
  표시하며 임의의 첫 검색 발언으로 대체하지 않는다. 초점별 선택은 의미 충족 판정이 아니다.
  모든 호출 전후와 최종 게시 전에는 원문·raw 화자·시각뿐 아니라 표시 화자의 일치도 검사한다.
  `source_focus_max_calls=1`인 기존 두 단계 모드는 빠진 항목 또는 형식을 한 번만 보완한다.
  두 단계 모두 처음 입력한 packed 번호만 허용하고 같은 입력·출력 상한을 따른다.
  복합 질문의 두 번째 선택은 전체 계획을 다시 작성해 중복·보조 선택을 교체할 수 있다.
  첫 계획보다 근거가 배정된 항목 수가 줄거나 형식·번호·예산 검사를 통과하지 못하면
  첫 유효 계획을 유지한다. 이 개수 비교도 선택 기록의 비교이며 의미 검증이 아니다.
  기존 두 단계 모드의 복합 선택 입력은 동일한 실제 회의·원문 번호·화자·시각·parent의 전체 필수 문맥만
  한 묶음으로 합친다. `source_turns`는 회의별 실제 원문 순서로 각 발언을 한 번만 표시하고
  packed 발언에는 직접 선택할 `id`를 함께 둔다. 독립 묶음은 순서 있는 `turn_keys`로
  문맥을 가리키며 `selectable_ids`에는 원래 packed 선택 번호만 둔다. 자기 원문 한 개만
  드는 선택은 직접 표시된 `id`와 기본 비용 1로 표현해 별도 비용행을 반복하지 않는다.
  packed 원문의 문자열 key는 `s{id}` 규약으로 유도해 같은 번호를 반복하지 않는다.
  일부만 겹치는 문맥은 합치지 않는다. 문맥 전용 ACK나 packed 밖 문맥에는 문자열 식별자만 두고 원문
  그대로 표시할 수 있지만 선택 번호로 승격하지 않는다. 묶음별 비용과 문자열 `source_key`로
  공유 문맥을 중복 계산하지 않게 하고,
  서버는 실제 현재 원문으로 펼친 전체 인용·필수 문맥의 합집합이 8개 안인지 검사한다.
  ACK는 비용에 포함해도 모델이 선택할 번호가 아니며, 추가 지시문·첫 계획 메타데이터의
  최대 공간을 첫 입력부터 예약한다. 긴 원문이나 JSON을 중간에서 잘라 넣지 않는다.
  원문 인용 요청은 추가 선택을 하지 않는다. 복합 질문의 첫 출력이 필수 필드·타입·
  번호 검사를 통과하지 못하면 같은 후보에서 엄격한 JSON으로 한 번 재선택한다.
  잘못된 첫 응답은 근거로 전달하지 않고, 재선택 후 별도 누락 보완이나 세 번째 호출을
  하지 않는다. 선택한 전체 계획의 필수 원문 문맥을 보존하며 추가 선택 오류는 첫
  유효 근거를 유지한다. 두 단계 전후 편집·취소를 확인하고, 선택하지 않은 ACK를 포함해
  모델 입력에 보인 전체 실제 문맥의 신선도를 다시 검사한다.
  원문 변경을 감지하면 답변·이력을 남기지 않는다. 표시 이스케이프와 안내문을 포함한
  실제 전체 길이를 다시 확인해 문맥부터 전체 인용 단위로 줄이고 참조도 함께 줄인다.
  모델의 항목별 배정은 의미 연결 검증이 아니므로 운영 답변에 항목 매핑표로 표시하지
  않는다. 답변·이력·스트림은 각자의 실제 화자·시각·원문 인용과 범위 안내로 구성한다.
  길이 제한으로 근거·문맥이 빠졌으면 제한을 표시하며 선택 누락을 자료 부재로 바꾸지 않는다.
  실제 Wiki 합성 실패로 원문에 전환한 경우에만 내부 출처 enum을 원문 ID renderer에
  전달해 이번 답변에서 공개 Wiki 근거를 사용하지 못한 범위를 안내한다. 이는 공개
  문서가 존재하지 않는다거나 전체 업무가 미완료라는 뜻이 아니다. 이 안내도 원문
  경로의 동기 답변·스트림·이력과 전체 출력 길이에 함께 반영한다.
  이 보완은 누락 방지 수단이며 질문 항목의 의미상 완전성을 보증하지 않는다.
  원문 그대로 인용하는 요청은 선택 전에 검색 출처 범위를 제한한다. 이번 질의·주제
  검색의 양수 RRF parent와 그 회의의 설정 범위 안 실제 인접 청크, 또는 단일 명시
  주제가 현재 본문에 그대로 있는 보충 parent만 선택·폴백·자동 문맥에 사용한다.
  전체 원문에서 부여한 번호와 원래 parent 위치는 유지한다. 먼 일반 의도 검색의
  점수0 구간을 관련 원문으로 대신 내보내지 않으며 허용 구간이 없으면 답변을 확정하지
  않는다. 이는 모든 점수0 근거를 거절하는 규칙이 아니고 일반 복합 질문의 원인·후속
  보충은 유지한다. 검색 출처 경계이며 개별 문장의 의미상 정답을 보증하지는 않는다.
- 같은 명시 회의 또는 검색 첫 근거 회의에서 실제 색인의 인접 구간과 일반 원인·후속
  검색 관점을 제한적으로 보충한다. 기존 RRF 순서·점수와 날짜·raw 화자 필터를
  유지하며 현재 원문·영수증·embed의 일치를 다시 확인한다. DB는 lexical/no-follow
  부모와 일반 파일 inode를 읽기 전후 확인해 읽기 전용으로 연다. 후보는 parent와
  검색 관점별로 번갈아 넣으며 입력 예산 안에서 완전한 원문·JSON 단위만 사용한다.
  질문의 내용 주제가 달라질 때만 추가 주제 검색을 최대 한 번 실행해 일반 지시문이
  주제 단어를 압도하지 않게 한다. 후보 순서는 실제 주제 겹침을 일반 예정·보고 표현보다
  우선하며, 질문에 들어간 내용 단어를 독립 검색 관점으로 보충한다. 원인 질문의 발생
  경위·시간순서 문서·요청·후속은 별도 FTS 축으로 찾고, 기존 전체 청크 상한 안에서
  각 축의 첫 유효 후보와 실제 인접 청크를 우선한다.
  원인 질문이 완료·현재/향후 상태도 물으면 조치·완화·중재 보고 축과 기존 인접 구간을
  같은 상한 안에서 보충한다. 조치 단어가 있다는 사실만으로 완료를 판정하지 않는다.
  `최근/최신`이 있고 회의·날짜
  필터가 없으면 이미 검색된 현재 관련 후보 중 원문·영수증·보존 날짜가 일치하는
  가장 최근 날짜의 회의를 선택한다. 언어 간 문자 일치가 없어도 실제 vector/both
  검색 후보는 비교 대상이며, 이 선택 자체는 사실 지지의 의미 판정이 아니다. 명시한 날짜·시각의
  회의는 유효한 전체 timestamp ID·보존 날짜·현재 색인/원문이 유일하게 일치해야 한다.
  구조화된 회의·날짜 필터가 항상 우선하고, 여러 명시 시각·잘못된 ID·모호한 같은 분의
  복수 회의는 임의로 고르지 않는다. API 날짜 필터와 자연어 시각의 추가 결합은 하지 않는다.
  `speaker_filter`는 검색 청크뿐 아니라 개별 발언 후보·자동 연결 문맥·최종 재검증에도
  적용한다. 여러 화자가 포함된 청크에서 요청하지 않은 화자의 발언을 직접 선택할 수 없다.
  지난 회의와 이번 회의처럼 회의 간 변화를 비교하는 요청은 허용된 여러 회의의 근거를
  보존한다. 비교 요청이 아닌 최신 회의 선택과 명시된 회의·날짜 제한은 그대로 적용한다.
  연결 어미로 끝난 선택 발언은 바로 다음 실제 동일 화자 원문이 후보에 있을 때만
  별도 인용으로 보존한다. 서로 다른 화자의 문구를 한 문장으로 합치지 않는다.
- 인용마다 선택 필드 `quote`에 실제 `text`, `speaker`, `start_time`, `end_time`을

  화자·미리보기·정확한 이동 시각을 우선 사용한다. 원문 속 마크다운과 가짜 참조 표시는

  같은 답변을 보내며, 편집 epoch·취소·세션 저장 경계를 유지한다.
- 새 주제가 없는 `그건 누가 확인하나요?` 같은 후속 질문은 세션의 최근 사용자
  주제 질문만 신뢰하지 않는 검색·선택 힌트로 사용한다. 이전 AI 답변은 근거뿐 아니라
  검색·모델 입력에서도 제외하며, 현재 원문 후보만 인용할 수 있다. 새 명시 주제나
  회의·날짜·화자 필터가 있으면 힌트를 상속하지 않고, 힌트도 같은 입력 예산에 포함한다.
- `chat.source_bound_answers`의 기본값은 `true`이며 일반 대화·창작·번역은 기존
  자유생성 경로를 사용한다. 선택 발언 수는 `source_answer_max_items`(기본 8), 보충한
  전체 청크 수는 `source_context_max_chunks`(기본 15), 인접 청크 범위는
  `source_neighbor_window`(기본 1)로 제한하고 기존 모델 입력·출력 예산을 함께 따른다.
  `source_coverage_passes`(기본 1, 허용 0 또는 1)가 0이면 초점 분리와 추가 호출을 끈다.
  1이면 `source_focus_max_calls`(기본 4, 정수 1~4) 안에서 초점을 묶어 순차 선택한다.
  이 값이 1이면 기존 두 단계 선택 모드를 사용하며 추가 선택은 최대 한 번이다.
  초점별 직접 선택은 `source_focus_max_items`(기본 3, 정수 1~16)와 전체 인용 상한 중
  작은 값으로 제한한다. 검색 우선순위는 해당 초점의 내용 단어를 별도로 가중하며,
  이 순위나 모델 선택 순서가 사실 지지·질문 충족을 증명하지는 않는다.
  활용된 확인·공유 동사와 종료·추후·검증 표현은 일반 질문 축으로 다루고 실제 주제
  명사와 구분한다. 문장 끝 온점으로 질문을 나누되 소수점과 인용 안의 온점은 보존한다.
  `결정하는 것과 … 공유` 같은 실제 명사화 병렬 표현도 질문 초점으로 나눈다. 시간·기간은
  구체적 질문 표현과 함께 확인하며, `점유시간` 같은 주제 이름만으로 시간 질문을 만들지 않는다.
  인용 밖에서 절 끝에 `요일·시간`을 명시한 경우에도 시간 단서를 적용한다. 영문·숫자
  토큰 뒤 목적격 조사로 끝난 미완결 발언은 최종 선택 순위만 낮추며, 유효한 인용 후보에서
  삭제하거나 새 문맥을 붙이지 않는다.
  같은 화자의 바로 이어진 발화에 걸친 관찰 범위 표현도 연결 문맥으로 보존하며,
  검색 순위의 시제·조건 단서만으로 실제 완료·미완료를 판정하지 않는다.
  술어가 끝나지 않은 시간 부사절과 유한한 동사 관형형도 같은 확인된 화자의 바로 다음
  실제 발언으로 이어 읽는다. 사람 이름의 같은 글자나 다른 화자·떨어진 발언으로 연결하지 않는다.
  필요·불필요를 서술하는 유한한 종결 표현 뒤에 같은 확인된 화자의 지시어로 시작하는
  미완결 이유절이 바로 이어지면 두 발언을 필수 문맥으로 함께 보존한다. 질문·요청·
  청유, 발언 누락, 다른 화자·미확인 화자, 주제 전환과 독립적으로 끝난 이유 문장은
  이 추가 연결에서 제외한다. 한쪽만 예산에 맞는다고 잘라 게시하지 않으며, 원문 한
  문장 그대로 인용하거나 응답 문맥을 끄는 경로에는 이 추가 연결을 적용하지 않는다.
  다른 선택의 문맥으로 포함된 문구도 모델이 실제 선택했다면 자신의 전체 문맥을
  검사한다. 모든 실제 선택 번호 중 함께 표시되는 요청의 QA·ACK까지 유한 반복으로
  닫은 뒤 전체 묶음의 예산을 검사하며, 요청만 남겨 내보내지 않는다. 자신의 필수
  문맥 전체가 이미 포함된 때만 중복 확장을 생략하고 실제 문구·각자의 출처를 유지한다.
  인용 상한 8개는 모든 호출의 최종 원문과 필수 연결 문맥의 합집합에 적용한다.
- 화자 표시명은 회의 전체 발화의 첫 등장 순서에 결합한다. 기존 Viewer 본문·복사의
  번호를 유지하도록 `UNKNOWN`의 자리도 보존하며, 미확인은 `참석자 ?`, 사용자가
  붙인 이름은 그대로 표시한다. 전사·검색·채팅 참조의 선택 필드 `speaker_labels`가
  같은 대응표를 전달하며 원문 ID·화자 필터·저장된 발화는 바꾸지 않는다. 검색 시에는
  Viewer와 같은 우선순위의 원문을 no-follow로 읽고, 확인할 수 없으면 원문 ID를
  그대로 표시한다. 답변 프롬프트에도 대응표의 회의 범위를 명시하며, 표시 번호를
  실명이나 회의 간 동일 인물의 근거로 사용하지 않는다.

## 수동 수정, 이력, 관련 기록

Wiki 상세 화면의 `수정`은 본문만 편집한다. 기존 회의 인용과 메타데이터는
보존한다. 사용자가 `원문과 비교해 내용을 검토했습니다`를 선택한 사실은
`human_reviewed`로 저장하며 AI 검사 결과와 구분한다. 검토 필요 페이지를
수정·검토해도 자동으로 확정 결정으로 승격하지 않는다.

AI 재검수 기록은 `ai_reviewed_at`, `ai_review_result`, `review_detail`로 별도 보존한다.
화면에는 `AI 재검수 일시`, `AI 재검수 결과`, `검수 메모`로 표시한다. 결과 값
`held`·`verified`·`historical`·`identity_unresolved`는 각각 `추가 근거 필요`·
`근거 확인됨`·`과거 버전`·`화자 이름 확인 필요`로 보인다. 메모는 평문으로 표시하며,
이 값으로 `human_edited`·`human_reviewed`를 설정하거나 보류 문서를 자동 게시하지 않는다.

- `GET /api/wiki/pages/{type}/{slug}`는 전체 문서의 SHA-256인 `revision`,
  `editable_content`, 사용자 수정·검토 표시와 `related_pages`를 반환한다.
- `PUT` 같은 주소에 `{content, expected_revision, reviewed}`를 전송한다.
  화면을 연 뒤 다른 작업이 수정했으면 409로 거부하고 입력을 유지한다.
- `GET /api/wiki/history/{type}/{slug}`는 최초 원본·현재·과거 버전을 반환한다.
- `POST /api/wiki/restore/{type}/{slug}`에 `{revision, expected_revision}`을
  전송하면 이전 본문을 새 수정본으로 저장한다. 기존 버전을 삭제하지 않으며
  복원한 내용은 다시 검토할 수 있도록 검토 완료 표시를 해제한다.
- 수정·복원은 기존 loopback/Origin 보호를 적용하고 경로·symlink를 검증한다.
  여러 저장소 인스턴스의 게시와 수동 편집은 루트별 잠금으로 직렬화한다.
- 사용자 수정·검토가 표시된 페이지는 자동 생성이 덮어쓰지 않는다. 새 AI 결과는
  별도 검토 후보가 된다. AI 출력에 복사된 사용자 검토 표시도 제거한다.
- 직접 연결·역링크·공통 프로젝트·관련 인물을 통해 다른 Wiki로 이동한다.

키워드 검색은 저장 직후 갱신한다. 본문 저장 뒤 검색 갱신만 실패하면 저장 성공과
검색 갱신 필요를 구분해 응답한다. 수정 전 벡터는 새 본문과 해시가 일치할 때까지
의미 검색에서 제외한다. Wiki 컴파일러의 다음 증분 임베딩 때 다시 반영되며,
그전에는 최신 키워드 검색을 사용할 수 있다.

원문 검색에서는 작은따옴표 한 쌍으로 명시한 주제 또는 한두 단어의 검색어를 모두
포함한 FTS 후보가 기존 상위 결과에 없을 때만 해당 후보 한 개를 마지막 자리에
보존한다. 회의·날짜·화자 필터와 최신 원문 검사를 통과한 후보만 사용하며, 영문·숫자는
낱말 경계를 지킨다. 기존 RRF 가중치와 `k`(기본 벡터 0.6·FTS 0.4·`k=60`), 점수는
바꾸지 않고 선택된 결과를 원래 점수 내림차순으로 반환한다. 긴 일반 질문·복수 주제
비교·FTS 가중치 0·일치 후보가 없는 경우에는 기존 결과를 유지한다.

## 검증 경계

요약 생성은 단일 호출·부분 요약·최종 통합·사용자 프롬프트 로드 실패 경로에 같은
근거 보존 지시를 붙인다. 기존 사용자 서식은 보존하며 화자 집합 밖의 참석자 생성,
호명만으로 실명 연결, `UNKNOWN` 임의 매핑, 요청자의 담당자 확정을 금지한다.
요청·약속·확정·가능성·완료·조건과 후반 정정을 보존하고, 수치의 단위·분모·측정
대상·지역·모델·방법별 비교 기준을 섞거나 불명확한 수치·약어를 추측해 복원하지 않는다.
이는 향후 생성의 예방 지시이며 정확도 향상을 보증하지 않는다. 이미 생성된 회의록의
주체·수치·부정·확정 강도 등 주요 주장은 원문과 대조하는 별도 의미 검수가 필요하다.

백엔드의 `generation_tokens` 실측값이 설정된 `summarize_max_tokens` 이상일 때만
원문과 사용자 서식을 유지한 간결한 요약을 같은 상한으로 한 번 재시도한다. 재시도도
상한에 도달하면 `SummaryError`로 실패시키고 기존 실패 폴백을 따른다. 실패한 부분
요약은 해당 원문으로 대체한다. 통합 실패는 기존 실패 표시와 화자 표기를 유지한 채
전체 원본 발화를 첨부하며, 검증되지 않은 부분 AI 요약을 결과에 포함하지 않는다.
통계가 없거나 유효하지 않으면 추가 호출 없이 기존 응답을 사용하며, 문장 끝 모양으로
완결을 추정하지 않는다. 실행 중 이미 로드된 모듈에 이 변경이 소급 적용되지는 않는다.

단위·API·경합 테스트는 사용자 데이터 대신 격리된 폴더·체크포인트와 모델 응답
대역을 사용한다. 브라우저 테스트는 실제 WikiView/API 클라이언트로 수정·검토·충돌·
복원·관련 기록 이동을 확인한다. 실제 로컬 모델의 가상 문장 검사도 사람 정답이
있는 긴 회의 전체 평가와 구분한다. 모델 응답에는 오탐·미탐이 남을 수 있다.

## 회의 처리 중 Wiki 진행 표시

Wiki가 활성화된 전체 처리에서는 전사·교정·요약·검색 반영을 마친 뒤에도 Wiki가
끝날 때까지 파이프라인을 `running`, `current_step=wiki_compile`로 유지한다.
화면에는 `전사·요약·검색 완료 · Wiki 정리 중`을 표시한다. 이미 준비된 회의록과
검색 결과는 사용할 수 있으며, 전체 완료는 Wiki 단계 결과를 저장한 뒤 게시한다.
Wiki 예외는 회의록·검색의 완료를 취소하지 않고 경고와 별도 실패 결과로 남긴다.

Wiki는 기존 여덟 단계의 재개 순서인 `completed_steps`에 추가하지 않는다.
성능 통계가 없어도 시작·종료 이벤트를 전달하며, Wiki에는 추정 백분율이나 ETA를
만들지 않는다. 표시하는 경과 시간은 실제로 관찰한 시작 또는 완료 이벤트를 따른다.
전체 처리 시간 로그에는 Wiki 실행 시간도 포함한다. Wiki 비활성 경로는 기존
여덟 단계 완료 동작을 유지한다. 여덟 단계 완료 뒤 Wiki 실행 중 중단됐고 종료
결과가 없으면, 재개 시 자동 재실행 없이 중단 경고와 비치명적 실패 결과를 한 번
남긴다. 경과 미확정은 `elapsed_known: false`로 구분해 0초 실측으로 표시하지 않는다.

## 앱 번들의 기존 회의 백필

소스를 포함하는 `.app`는 Wiki API가 지연 import하는 `scripts/__init__.py`와
`scripts/backfill_wiki.py`를 반드시 포함한다. 기존 CoreAudio 런타임 helper인
`scripts/zoom_audio_activity.swift` 외에 설치·빌드·벤치마크 스크립트는 포함하지
않는다. 빌더는 필수 Python 파일의 누락·symlink를 거부하고, 검증기도 이 두 파일의
누락과 `scripts/` 안의 allowlist 밖 파일을 실패로 판정한다.

생성 런처는 첫 Python 실행 전에 `PYTHONDONTWRITEBYTECODE=1`을 내보낸다.
네이티브 창·서버 자식 프로세스에도 상속해 실행 중 번들에 Python 캐시가 생기지
않도록 한다. 캐시를 허용하도록 번들 검증 기준을 완화하지 않는다.

기존 회의 네 건만 다시 검사하려면 `POST /api/wiki/backfill`에 다음처럼 대상 ID를
명시한다. 실제 요청에는 자리표시자를 각 회의 ID로 바꾼다.

```json
{"meeting_ids": ["meeting_id_1", "meeting_id_2", "meeting_id_3", "meeting_id_4"], "dry_run": false}
```

Wiki가 활성화돼 있고 전역 `wiki.dry_run`도 false여야 실제 컴파일한다. 요청의
`dry_run: true`는 모델 호출 없이 대상 수만 확인하며, 완료 상태·원문·요약·회의
날짜의 실행 적격성을 검증한 결과는 아니다. 명시적 대상은 기존 Wiki 결과가 있어도
다시 컴파일하며 별도의 `force` 필드는 없다. 완료된 전사·요약은 다시 만들지 않는다.

202 응답의 `job_id`로 `GET /api/wiki/backfill/{job_id}`를 조회한다. 화면은
`/app/settings/wiki-backfill`에서 확인한다. `processed`, `total`, `status`와
`published`, `pending`, `empty`, `failed`, 각 페이지 수·오류를 구분한다.
`published`는 액션 목록을 포함한 공개 페이지가 생성·갱신된 회의 수이며 확정
결정 수가 아니다. 진행 콜백은 회의 하나가 끝난 뒤 갱신되므로 첫 긴 회의를
처리하는 동안에는 진행 수가 0일 수 있다. 앱 갱신이나 백필 작업의 종료만으로
기존 모든 후보가 의미 검수를 통과했거나 전체 처리가 성공했다고 판단하지 않는다.

개발 checkout 또는 editable 설치가 누락을 가리지 않도록 실제 소스 번들을
만들어 빈 디렉터리에서 `python -I -S -B`로 import를 검사한다. 이 검사는 앱 실행,
모델 로드, 실제 회의 백필을 수행하지 않는다.

```bash
pytest tests/test_build_launcher_app.py tests/test_validate_launcher_app.py -q
```
