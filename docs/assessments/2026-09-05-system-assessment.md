# Recap 심층 평가와 사업화 우선순위

평가일: 2026-09-05 · 소스: `main` / `e3e4b61f2d5730e257fa46b79a06bcf1e09d575e`

사용자 요청에 따라 기능 오류, 개선 필요사항, 수익·유입 전략 전담 서브에이전트
3개가 독립 분석했고, 통합 검토자가 주요 코드 경계와 재현 결과를 교차 확인했다.
이 문서는 관찰 사실, 미실행 검증, 제품 제안, 사업 가설을 구분한다.

## 종합 판단

**Recap은 기능이 풍부한 개인 업무용 알파 제품이며, 지금 가장 중요한 투자는
수정·검색·근거의 일관성과 비개발자의 첫 성공을 완성하는 것이다.**

로컬 녹음부터 전사, 화자분리, 교정, 회의록, 검색, 채팅, Decision Wiki까지
가치 사슬이 길다. 모델 직렬화, 체크포인트, 취소 후 정리 보호, 회의별 변경 잠금,
외부 업로드 동의, 데이터 보존 설계는 의미 있는 기반이다. 기존 STATUS의
안정화 작업을 무시하고 큐·timeout 문제가 모두 남아 있다고 판정하지 않았다.

그러나 사용자가 고친 값과 AI가 회수하는 값이 달라질 수 있고, 조건을 붙인 질문의
검색 범위도 일부 경로에서 유지되지 않는다. ‘신뢰할 수 있는 회의 기억’을 유료
가치로 팔려면 이 일관성을 먼저 입증해야 한다. 일반 사용자 대규모 유입 확대는
설치·품질·복구 경험을 검증한 뒤 진행하고, 초기에는 지원을 포함한 소규모 파일럿이
적합하다는 판단이다. 실제 사용자수·매출·유지율 자료가 없어 PMF는 평가할 수 없다.

F1/F3/F4는 각각의 패치와 함께 **원문 revision과 파생 산출물 상태를 연결하는
공통 설계**가 필요하다. 단, 사용자가 편집한 회의록을 자동 덮어쓰는 방식은 피한다.
내구성 있는 변경 의도/재색인 대기 표시 → 원문 revision 게시 → 순차 갱신 → 새
인덱스 버전 게시 → 상태 확인 순서를 기존 회의별 mutation coordinator와 결합한다.
파일·SQLite·Chroma를 하나의 원자 transaction처럼 취급하지 않고 crash 뒤 재조정한다.
회의 날짜는 출처와 함께 안정 메타데이터로 저장해 재생성 날짜와 분리한다. 기존
인덱스 날짜나 DB 등록 시각을 검증 없이 실제 회의일로 확정하지 않는다.

F2는 router_enabled 기본 False인 선택 기능의 문제다. 범위 필터를 Wiki에서 제대로
해석할 수 있기 전에는 해당 질문을 RAG로 보내는 수정 범위가 작다. F6는 서버 측
경계 누락이며 실제 브라우저 연결 성공은 로컬 네트워크 권한·혼합 콘텐츠 정책 등에
영향받는다. 오디오 본문 유출이나 모든 브라우저에서의 공격 성공을 확인한 것은 아니다.

## 3. 수익과 유저 유입 전략

### 고객과 가치 제안

첫 고객은 **Apple Silicon을 쓰며 한국어 고객/프로젝트 회의를 반복하고, 회의 뒤
결정·담당자·배경을 다시 찾는 PM, 컨설턴트, 소규모 에이전시 리드**로 좁힌다.
한국어·로컬 선호·반복 회의·결정 회수의 필요가 함께 있는지를 인터뷰로 확인한다.
모든 Mac 사용자, 대기업 전사 협업, 의료·법률 등 엄격한 요구가 있는 업종으로
동시에 확장하지 않는다.

제안 메시지는 ‘한국어 회의에서 누가 무엇을 왜 결정했는지, 원문 근거와 함께
내 Mac에서 다시 찾기’다. 로컬 전사·요약만으로 차별화하기에는 경쟁 제품의
기능 범위가 넓다. 유저가 실제로 시간을 절약하는 단위는 전사 분량보다
‘결정 근거를 찾아 확인한 업무’다.

기본 Wiki는 활성화·실작성·라우팅이 각각 설정에 의해 제한되어 있다.
[설정 기본값](/Users/youngouksong/projects/meeting-transcriber/config.py:1038)을
그대로 쓰는 신규 유저가 광고의 핵심 가치를 경험하도록, 첫 회의에서 결정 생성과
원문 인용 확인까지 연결해야 한다. 이는 실제 실행 중인 사용자의 설정을 조회한
판정이 아니라 저장소 기본 설정에 대한 관찰이다.

### 유료 상품의 순서

1. **설치 지원 파일럿:** 10~20명 적합 고객에게 설치·첫 회의 검증·피드백을 제공한다.
   수작업 지원시간을 기록하고, 무료 호의와 실제 지불 의사를 구분한다.
2. **개인 Pro:** 안정된 배포 앱, 버전 복원, 업무 템플릿, 내보내기와 업데이트 편의의
   묶음으로 가격을 실험한다. 일회성 라이선스라면 업데이트 권리 기간을 명확히 하고,
   무기한 지원을 원가 계산 없이 약속하지 않는다. 연간 요금과 비교 실험할 수 있다.
3. **팀 도입 파일럿:** 공유 워크스페이스가 없어도 설치 지원·팀 템플릿·도입 교육은
   판매 실험이 가능하다. 다만 현재 없는 동기화·권한·관리 기능을 SaaS 좌석 상품처럼
   약속하지 않는다. 실제 팀 내 공유 수요를 확인한 뒤 구축한다.

초기 가격 가설은 설치·업무 적용 파일럿 **149,000원/인 1회(총 2시간 지원 한도)**,
설치가 안정된 개인 제품은 **79,000원 대 99,000원(12개월 업데이트 포함)**이다.
이후 선택적 유지보수 **39,000원/년**은 갱신 가치가 확인될 때 시험한다.
확인된 고객 지불의사나 현재 판매 중인 상품 가격이 아니다.

MIT 코드 사용권과 모델 사용·재배포 조건은 별개다.
[EXAONE 3.5 공식 LICENSE](https://huggingface.co/LGAI-EXAONE/EXAONE-3.5-7.8B-Instruct/blob/main/LICENSE)는
비상업 조건과 별도 상업 계약을 명시하므로 상용 구성 검토가 필요하다.
실제로 배포하는 Gemma 양자화 artifact도 라이선스와 리비전을 확인해야 한다.
세부 공식 자료와 가격 가설은 사업 전담 보고서에 정리한다.

### 지표 정의와 수익 계산

- 첫 가치 도달: 설치 뒤 첫 실제 회의를 처리하고 결정/액션을 확인한 뒤 원문 인용을
  열거나 업무 결과를 내보낸 적합 신규 사용자 비율. 버튼 클릭만으로 세지 않는다.
- 핵심 Activation: 적합 사용자가 설치 후 7일 이내 본인 회의 2건을 성공 처리하고,
  이전 결정을 질문으로 찾은 뒤 실제 원문 시각을 확인한 비율.
- Retention: 활성화 코호트 중 2주/4주 뒤에도 새 회의를 처리하거나 과거 결정 근거를
  업무에 사용한 비율. 표본 수와 관측 기간을 함께 보고한다.
- 제품 가치: 사람이 최종 회의록을 고치는 시간, 올바른 근거를 찾는 성공률/시간,
  결정·담당자·숫자 오류, 결과의 업무 재사용.
- 운영 원가: 고객당 설치/지원 분, 환불, 다운로드·배포 비용, 업데이트 유지 비용.
  로컬 추론으로 서버 비용이 낮아도 지원·개발 비용이 사라지는 것은 아니다.
- 선택 동의 없는 원문/음성/프롬프트 수집은 도입하지 않는다. 초기에는 로컬 집계와
  인터뷰·설치 지원 기록만으로도 가설을 검증할 수 있다.

매출 기본식은 `적합 방문 × 설치율 × 활성화율 × 유료전환율 × 실현 가격`이다.
일회성 매출, 연간 계약의 현금 수취, MRR을 섞지 않는다. 구체적인 가격·매출
시나리오는 관측치가 아닌 가정이며 사업 보고서의 산식으로 확인한다.

예를 들어 79,000원 제품을 월 20명 구매하면 현금수입은 158만원이다.
환불충당 5%, 결제비 3.5%, 지원 30분/인, 지원 시간원가 40,000원/시간을 가정하면
세금·광고·고정 개발비 차감 전 간이 공헌 현금은 **1,045,700원**이다.
지원이 2시간/인으로 늘면 **-154,300원**이다. 이는 수요 예측이 아니라
설치 지원 비용에 대한 민감도이며 ‘로컬이라 운영비가 없다’는 가정을 경계하게 한다.
